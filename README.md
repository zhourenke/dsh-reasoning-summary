# @zhourenke/dsh-reasoning-summary

**让看不到自己思考的模型，看见自己的内心。**

DSH 默认会保留模型的思考过程并把它传进下一步循环，思考的连续性和对历史思考的可见性都由此得到保证——**只有触发上下文压缩时才会丢**。所以对能看见自己思考的模型来说，这件事本来就是解决的。

出问题的是**闭源模型**：它们的加密思考不会完整进入 DSH 上下文，DSH 也无法使用这些 provider 的原生状态去接续。于是每进入下一步循环，模型都要从头推测"我上一步做了什么、接下来该做什么、再往后怎么走"，而这份推测到下一步又会重新来过——白花大量时间，也白烧大量 token。

本插件补的就是中间缺的这一环：它让被选中的路由在调用工具前，用**可见文本**留下一句简短的行动摘要，插件把这句话规范化后写进会话历史。下一步——以及之后的每一步——于是能直接读到上一步在做什么、依据是什么、接下来要做什么。**它只影响被选中的路由，不改动其它模型，也不隐藏任何历史。**

## 它解决什么问题

- **加密思考的缺口**：闭源 provider 的加密推理不会完整进入 DSH 上下文，也无法用 provider 原生状态接续；插件把"上一步做了什么"变成模型自己能读到的普通历史。
- **省下重复推导的时间与 token**：模型不必每一步都重新推测自己的上一步，尤其是在长工具循环里反复消耗的那部分。
- **换模型也不断线**：摘要作为普通会话历史传递，中途切到别的模型同样读得到。
- **只对你选中的路由生效**：`provider` + `model` 精确匹配，其它模型完全按原来的方式工作。
- **历史不会被藏起来**：摘要以普通消息追加，不安装任何路由过滤器、不遮蔽任何消息。
- **随时可卸**：作为 profile 层插入，不修改 DSH 本体；把列表清空就完全关闭。

## 安装

```powershell
dsh plugin --profile web add "github:zhourenke/dsh-reasoning-summary"
```

**安装后需要重启 DSH**——bundle 集合是进程启动时的快照，重启之前新插件不会被加载，刷新页面也没有用。本插件是双半边插件，重启之后还要**刷新一次页面**，设置里的卡片才会出现。

卸载：

```powershell
dsh plugin --profile web remove @zhourenke/dsh-reasoning-summary
```

## 快速上手

插件默认**完全关闭**（`models` 为空）：不注入提示、不改动任何流、不产生任何摘要。

最省事的开法是在界面里点：打开 **设置 → 插件 → 推理摘要**，在模型列表里勾选要触发的路由，保存即可。这张卡片读的是 DSH 实时的模型目录，模型当前不可用也不会让已保存的条目消失。

也可以直接改配置文件 `<harness home>/settings.yaml`（Windows 上是 `%USERPROFILE%\.dsh\settings.yaml`）。它是按 namespace 分节的，本插件的 namespace 是 `reasoning-summary`：

```yaml
reasoning-summary:
  models:
    - provider: <provider-id>
      model: <model-id>
```

`provider` 与 `model` 必须与 DSH 里实际的 id 逐字一致，两个都要匹配——填错的条目不会报错，只是永远不生效（用设置界面的列表勾选就不会写错）。

**保存即生效，两边都不需要重启。** `settings.yaml` 是热重载的（文件监听默认开启，写入与重载由同一条操作链串行化，不会读到写了一半的文件），改完立刻作用于后续步骤。只有**安装或卸载插件本身**才需要重启——这两件事经常被混为一谈，结论正好相反。

确认它在工作：让被选中的模型调用一次工具，然后看两处——模型会在可见文本里输出 `<summary>…</summary>`，下一步会收到一条 `[Action summary]` 记录。如果模型漏写了，你会看到 `[Action summary: missing]`，那是插件在提醒它补上。

## 配置

| 字段 | 类型 | 默认 | 说明 |
|---|---|:---:|---|
| `models` | array | `[]` | 触发路由列表，每项为 `{ provider, model }`。**空列表是唯一的关闭状态**，也是默认值。 |

取值规则：

- `provider` 与 `model` 必须**同时**匹配；同一个 model 挂在另一个 provider 下不会启用那条路由。
- 一个条目的 provider 或 model 写错不会报错，只是那条规则永不生效——它们必须与 DSH 里实际的 provider id、model id 逐字一致（在设置卡片里勾选就不会写错）。
- schema 只保留 `models`，旧版本留下的无关字段会在读取时被归一化丢弃，不会导致加载失败。
- 设置卡片只改本插件的 namespace，不会动 DSH 通用的模型设置；模型目录里当前不可用、但已被启用的条目会保留在末尾的「已保存但当前不可用」分组里，等你手动取消勾选。

## 插件要求模型做什么

启用后，插件会在被选中路由的系统提示里加入一段要求：**在调用工具之前，先用可见文本写一句行动摘要**，格式是一个字面标签：

```xml
<summary>target, concrete evidence or current state, and the immediate operation or decision</summary>
```

摘要是**给下一步看的执行记录**，不是状态播报：相关的用户请求、涉及的文件 / 函数 / 命令、已经确认的观察或结果，以及紧接着要做的动作或决定，都该写进去；"继续分析""检查实现""取得进展"这类无法据此行动的话没有意义。

判定只看**可见文本**：只写在推理 / 思考内容里的摘要，插件看不到，等同没写。摘要还必须出现在第一个工具调用之前。

如果模型在标签之外还输出了普通文案，插件会在该步骤结束时把这些文本从界面流里移除（工具块的原有顺序不变），免得界面里出现一段没有上下文的内部进度。如果 provider 以 `error` / `aborted` 结束、或者流本身抛了异常，那么已经发出工具调用的失败尝试同样会隐藏缓冲文本，但**不会**生成任何记录——失败的进度不会被当成完成的执行记录。

模型漏写时，下一步会带上这段提醒：

```text
Missing action summary: no <summary> tag was received in visible text — reasoning/thinking content is never read, and text outside the tag is discarded. Before your next tool call, emit the summary as visible assistant text in a literal <summary>...</summary> tag.
```

流在闭合标签之前就结束时（非失败），已收到的内容按不完整处理：

```text
Summary incomplete: the response ended before the closing tag; only a fully closed tag counts as a summary.
```

最终的普通答复**不要求**摘要，也不会产生记录；无工具的答复完全跳过摘要解析与标签移除，即使里面出现字面 `<summary>…</summary>` 也会原样保留。

## 摘要去了哪里

每个工具步骤的摘要都以普通 `user/message` 写入或排队，模型看到的是紧凑形式：

```text
[Action summary]
Read src/index.ts; confirmed the parser location; next update the nearest-pair regression.
```

只有不完整或缺失的状态才在标题里标 `partial` 或 `missing`。工具循环继续时，插件会等所有根工具调用的 durable `tool/result` 提交之后，才把摘要排进 Agent inbox；工具调用直接结束 turn 时，摘要也直接追加到 durable session。两种形式都留在正常会话历史里，任何后续 provider / model 都读得到，本插件不隐藏、也不改写已有历史。

模型只输出推理、既没有工具调用也没有可见答复时，插件会用公开的 `agent.steer()` 在**同一个 turn** 内请求继续，通知标题是 `[Continue after reasoning-only response]`，最多 3 次——避免一个反复只输出推理的模型把 turn 拖住。

## 什么时候生效

每个步骤在**准入时**采样一次当前路由与设置：

| 步骤准入状态 | 当前步骤的新行为 | 已有摘要历史 |
|---|---|---|
| 精确路由已启用 | 注入提示；处理当前流；可产生 relay 或 reasoning-only continuation | 完整可见 |
| 精确路由未启用 | 普通流原样通过；不注入提示；不产生新的 relay / continuation | 完整可见 |

已经准入的启用步骤拥有自己的流状态：模型切换或设置变更是发生在流进行中的话，**不会**取消、清空或改写这个步骤，它仍会写完摘要并持久化，变化只影响下一个步骤。下面这些行为因此都是有意设计的：

- A 启用 → B 禁用 → A 启用：B 能读到 A 的旧摘要但不产生新摘要，A 恢复后继续产生。
- 关掉设置再打开：关闭期间不产生摘要，旧摘要不消失，重新启用后从下一步骤恢复。
- A → B → C → D（A/C 启用、B/D 禁用）：四个模型都能读到完整的已有摘要历史，只有 A/C 的新工具步骤产生记录。
- 从禁用的 B 开始且历史为空：B 不产生摘要；之后切到启用的 A，从空历史开始生成第一条。

## 给 Agent 的要点

- 本插件不提供任何工具，但它会**改变被选中路由该输出什么**：调用工具前需要先给出可见的 `<summary>…</summary>`，只写在推理 / 思考内容里不算数。
- 它不改变会话历史的可见范围：摘要以普通消息追加，所有模型看到的历史是一致的。
- 摘要要具体到文件 / 命令 / 观察结果与下一步动作；空泛的表述对下一步没有帮助。
- 看到 `[Action summary: missing]` 或 `[Action summary: partial]`，说明上一条摘要没写全；看到 `[Continue after reasoning-only response]`，说明上一轮只有推理、没有动作也没有答复。
- 判断插件是否生效：**设置 → 插件**里能看到「推理摘要」卡片，并且工具步骤之后会出现 `[Action summary]` 记录。

## 它管不到什么

- **不屏蔽推理内容**：`reasoning_content` / thinking 照常传递；插件不选择屏蔽模型，也不删除历史里的 `thinking`。
- **不做工具门控或权限策略**：哪个工具能调用、能调用几次，不由本插件决定。
- **不隔离会话历史**：`models` 只决定"新步骤是否产生摘要"，不改变任何模型能看到的历史范围。
- **不改写历史里已有的摘要**：旧会话中的摘要按原样继续传递。

## 已知限制（实测确认）

- **摘要只在可见文本里找**：写在推理 / 思考内容里的摘要在插件看来是缺失的。这是有意的——模型的思考不会被误当成行动记录。
- **一个步骤只认第一个完整标签**：同一文本块内取最近邻的完整配对，前面的孤立开标签不会抢走后续配对；但一个步骤里写了多个摘要时，只有第一个作数。
- **continuation 有次数上限**：reasoning-only 的续写请求同一 turn 内最多 3 次，超过后该 turn 结束，不会无限续下去。
- **旧版本的遮蔽不可逆**：早期版本用 replacement 遮蔽过结束 turn 的摘要，那种遮蔽不会因为升级而自动恢复，受影响的旧会话需要单独的 raw-log 重建或迁移。当前版本不再使用 replacement。
- **安装与卸载需要重启**：bundle 集合在进程启动时确定；改配置则不需要。

## 兼容性

在 **DSH v0.1.5-rc.1**（2026-09）下测试通过。本插件是双半边插件：宿主半边改动需要重启 DSH，浏览器半边改动还需要刷新页面——这两条只针对插件开发，日常改配置不需要重启。
